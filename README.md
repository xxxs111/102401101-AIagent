## 一、这个项目做了什么

一个**校园失物招领**网页应用。校园卡、钥匙、水杯、雨伞、耳机、书籍最常丢，教学楼、食堂、图书馆、运动场是高频地点；本应用把散落在班级群、宿舍群、朋友圈的寻物与招领信息集中到一处，按时间倒序展示，支持关键词与多维筛选，让拾主和失主更快对上号。

**核心闭环（务必按顺序体验一遍）**

```
发布信息  →  浏览 / 搜索  →  查看详情  →  联系发布者  →  更新状态
  │             │                │             │              │
 表单校验  倒序列表+组合筛选   一键复制联系方式   标记已找到/已归还
```

**已实现功能清单**

| # | 功能 | 说明 |
| --- | --- | --- |
| 1 | 发布寻物 / 招领 | 类型切换，必填项前端校验，缺失时字段标红并给出具体提示 |
| 2 | 浏览列表 | 倒序展示；**进行中优先**，已完成的置灰并排到列表后方 |
| 3 | 搜索 | 关键词模糊匹配名称 / 描述 / 地点 / 分类，忽略大小写与首尾空格 |
| 4 | 组合筛选 | 首页：全部 / 寻物 / 招领 / 只看进行中；搜索页：关键词 + 类型 + 分类 |
| 5 | 查看详情 | 渐变大图、类型与状态徽章、时间地点行、描述、浏览数 |
| 6 | 联系发布者 | 一键复制联系方式（Clipboard API，失败自动降级 `execCommand`） |
| 7 | 更新状态 | 发布者本人可标记「已找到 / 已归还」、恢复为进行中 |
| 8 | 编辑 / 删除 | 发布者可修改内容、删除信息（删除前二次确认） |
| 9 | 我的发布 | 共发布 / 进行中 / 已完成统计 + 每条信息的操作入口 |
| 10 | 数据持久化 | `localStorage`，刷新不丢失；不可用时自动降级为内存存储 |
| 11 | 安全与健壮 | 所有用户输入经 `escapeHtml` 转义防 XSS；存储损坏自动降级为空数组 |

**明确不做的部分**（与原型边界一致）：不做后台管理、不做实名认证、不做即时聊天、不做地图定位、不做服务端与账号体系。

## 二、怎么运行（测试人员请看这里）

**环境要求：只需要一个 Chrome 浏览器。** 不需要 Node、不需要 Python、不需要任何构建步骤。

**方式一：本地直接打开（最省事）**

1. 下载 / 解压本项目全部文件；
2. 双击 `index.html`（或右键「打开方式 → Google Chrome」）；
3. 首次打开会自动载入 6 条演示数据，可以直接浏览、搜索、看详情。

> 注意：用 **Chrome** 打开。部分浏览器在 `file://` 协议下对剪贴板有限制，项目已做降级处理并给出 Toast 提示。

**方式二：起一个本地静态服务器（可选，更接近真实环境）**

```bash
# 在项目根目录执行任意一条
python -m http.server 8765
npx serve .
```

然后访问 `http://127.0.0.1:8765/index.html`。

**体验完整闭环的最短路径（约 1 分钟）**

1. 打开 `index.html` → 首页看到 6 条演示信息（进行中在前，已完成置灰在后）；
2. 点「🔍 搜索物品名称、地点、描述…」→ 输入 `保温杯` → 实时筛出 1 条；
3. 点任意卡片进详情页 → 点「复制」→ 联系方式进剪贴板；
4. 回首页点「🔍 发布寻物」→ **直接点「立即发布」**，会看到必填项标红；
5. 填完再发布 → 出现「发布成功」页 → 底部进「我的发布」→ 点「标记为已找到」→ 该条置灰并移到列表后方。

## 四、数据模型与关键实现

**一条信息（item）长这样**

| 字段 | 含义 | 取值示例 |
| --- | --- | --- |
| `id` | 自增主键 | 1, 2, 3… |
| `type` | 信息类型 | `lost`（寻物）/ `found`（招领） |
| `name` / `category` | 物品名称 / 分类 | 校园卡 / 校园卡、电子产品、水杯… |
| `time` / `place` | 丢失或拾取的时间 / 地点 | 2026-10-06 / 三区田径场看台 |
| `desc` / `image` | 补充描述 / 图片链接 | 蓝色卡套，卡号末尾 3721 |
| `contactName` / `contact` | 称呼 / 联系方式 | 李同学 / 13800001234 |
| `status` | 状态 | `active`（进行中）/ `done`（已完成） |
| `publisherKey` | 本机发布者标识 | 首次发布时生成的随机字符串 |
| `views` / `createdAt` / `updatedAt` | 浏览数 / 创建时间戳 / 更新时间戳 | 26 / 1727… |

**四个关键设计决策（博客里可以直接展开写）**

1. **状态文案统一由 `Utils.statusOf()` 输出。** `status × type` 两两组合出四种文案：寻物+进行中=「寻找中」、寻物+已完成=「已找到」、招领+进行中=「待认领」、招领+已完成=「已归还」。界面层只认这个函数，避免文案散落在十几个模板字符串里。

2. **没有账号系统，怎么知道谁是发布者？** 用 `publisherKey`：首次发布时生成一个随机标识存在 localStorage，「我的发布」只展示标识匹配的信息，详情页只有标识一致时才显示「标记完成 / 编辑 / 删除」。这既回答了「谁来改状态、从哪里改」，又没有引入作业明确不要求的账号体系。

3. **搜索是"组合过滤器"而不是简单 `includes`。** 关键词 + 类型 + 分类三个条件自由组合，关键词同时覆盖名称 / 描述 / 地点 / 分类，并且 `trim().toLowerCase()` 处理空格与大小写 —— 避免测试人员输入 ` 校园卡 ` 或 `airpods` 时误以为搜索坏了。

4. **排序规则：进行中在前，同状态按发布时间倒序。** 已完结的信息自动置灰、后置，详情页不再展示联系入口，从机制上减少无效联系。

**目录里能直接引用的关键代码位置**

- 本地存储封装与降级：`js/store.js` 中 `readRaw / writeRaw / loadItems / saveItems`
- 表单校验（16 类规则，逐字段返回错误）：`js/store.js` 中 `isValidPublishData`
- 组合搜索：`js/store.js` 中 `searchItems`
- 状态更新：`js/store.js` 中 `updateStatus`
- 防 XSS：`js/utils.js` 中 `escapeHtml`，模板层 `js/view.js` 里所有插值都经过它
- 一键复制（含降级）：`js/app.js` 中 `copyText`

## 五、单元测试

- **工具**：原生 JavaScript 手写断言（`assert.ok / equal / notEqual / deepEqual / throws`），**零框架、零依赖、离线可跑**。
- **规模**：**61 个用例**，覆盖 6 个模块 —— 工具函数 10、表单校验 11、数据读写 19、状态更新 13、搜索与统计 11、演示数据 5（含回归用例）。
- **构造测试数据的思路**：先 `resetStorage()` 清库保证隔离，再用 `fixtures()` 写入 4 条固定数据（含不同类型、状态、地点、联系方式格式），每个用例都能重复、可预期。
- **覆盖的场景**：
  - 正常：合法数据发布成功、状态流转、搜索命中；
  - 边界：名称正好 30 字 / 地点正好 50 字 / 描述正好 200 字 / 日期正好是今天 / 关键词带首尾空格 / 大小写不一致；
  - 异常：空表单、纯空格、超长文本、未来日期、非法联系方式、不存在的 id、非法状态值、存储内容被写坏、中文与 emoji 往返。

**测试真的抓出过问题**（这两条已经变成永久回归用例）：

| 问题 | 现象 | 修复 |
| --- | --- | --- |
| 校验把少一位的手机号当成合法 QQ 放行 | `1380000123`（10 位）被判为合法联系方式 | 纯数字串先走手机号规则，`1[3-9]` 开头但位数不对直接判非法；QQ 收紧为 5–11 位 |
| 非法月份不会报错 | `2026-13-01` 被 `new Date()` 静默溢出成 2027-01-01 | `parseDate` 增加月份 / 日期范围与溢出校验，非法直接返回 `null` |

## 六、已知限制与后续可以做的事

- 数据只存在**本机浏览器**，没有服务端，换电脑 / 换浏览器看不到彼此的信息 —— 这是本次作业「不做后台」的边界所决定的；
- 因此「联系发布者」走的是复制联系方式后线下联系，不做站内私信；
- 图片采用链接方式（原型里的图片上传），未做文件上传与压缩；
- 后续若要真正落地：接一个轻量后端（或用云开发）替换 `store.js` 的存储实现即可，因为界面层完全通过 `Store.*` 访问数据，替换成本低。
