# 开发文档 · 寻回（校园失物招领）

> 本文档给"读代码的人"看：分层怎么分的、数据怎么流的、为什么这么选、有哪些坑。
> 使用说明和验收流程见 `README.md` 与 `docs/验收与提交指南.md`。

---

## 一、技术选型与理由

| 决策点 | 选择 | 理由 | 被放弃的方案 |
| --- | --- | --- | --- |
| 形态 | 单页 Web 应用（PC Chrome 打开 `index.html`） | 与第一次作业原型一致；测试成本最低，助教双击即用 | 微信小程序（需要开发者工具与账号，助教无法快速验收） |
| 框架 | **不引入任何框架**，原生 HTML/CSS/JS | 作业要求"下载全部文件后用 Chrome 打开就能看到预期结果"，构建工具会引入环境依赖 | Vue / React（要 Node、要打包，验收门槛变高） |
| 视图组织 | `location.hash` 简易路由 + 字符串模板渲染 | 支持 `#/detail/3` 这类可直达链接，方便截图与问题复现；逻辑层可与 DOM 解耦，便于单元测试 | 多页面 HTML（页面间状态共享麻烦）、虚拟 DOM（过度设计） |
| 数据持久化 | `localStorage` | 无后端前提下的单机演示足够；刷新不丢数据 | IndexedDB（API 复杂，收益不明显）、后端数据库（超出作业边界） |
| 单元测试 | 原生 JS 手写断言 | 零依赖、离线可跑、控制台粘贴即可执行，符合作业附录的思路 | QUnit / Jest（需要下载文件或 Node 环境） |
| 身份识别 | 本机随机 `publisherKey` | 不引入账号体系，同时能回答"谁能改状态、从哪改" | 登录注册（作业明确不要求，且会让演示变复杂） |

## 二、分层结构

```
        ┌───────────────────────────────────────────────┐
        │  index.html          手机外框 / 标题栏 / 底部导航 │
        └───────────────────────────────────────────────┘
                              │
        ┌─────────────────────▼─────────────────────────┐
        │  app.js   界面层：哈希路由 / 渲染调度 / 事件处理   │
        └───────┬───────────────────────────────┬───────┘
                │ 读数据                         │ 取模板
        ┌───────▼─────────┐             ┌───────▼─────────┐
        │  store.js 数据层 │             │  view.js 模板层  │
        │  校验/增删改查/搜索│             │  数据 → HTML 串  │
        └───────┬─────────┘             └───────┬─────────┘
                │ 依赖                          │ 依赖
        ┌───────▼───────────────────────────────▼───────┐
        │  utils.js 工具层：转义 / 日期 / 状态文案 / 防抖   │
        └───────────────┬───────────────────────────────┘
                        │
        ┌───────────────▼───────────────────────────────┐
        │  localStorage（lf_items_v1 / lf_owner_v1）      │
        └───────────────────────────────────────────────┘
```

**关键约束：`utils.js` / `store.js` / `view.js` 三个文件都不访问 DOM。**
这是整个项目能被单元测试覆盖的根本原因 —— 业务规则（校验、搜索、状态流转、转义、模板输出）全部是纯函数，只有 `app.js` 负责和浏览器打交道。如果一开始把逻辑都写进 `onclick` 回调里，后面就只能靠人工点测，61 个用例无从谈起。

## 三、数据模型

### 3.1 item 结构

```js
{
  id: 3,                          // 自增主键（generateId 取当前最大值 + 1）
  type: 'lost',                   // 'lost' 寻物 | 'found' 招领
  name: '一串钥匙（带小熊挂件）',
  category: '钥匙',                // 白名单见 Store.CATEGORIES
  time: '2026-10-06',             // YYYY-MM-DD，不允许晚于今天
  place: '体育馆羽毛球场地',
  desc: '三把钥匙 + 一个棕色小熊挂件……',
  image: '',                      // 图片链接，空串表示不展示
  contactName: '张同学',
  contact: '13900005678',
  status: 'done',                 // 'active' 进行中 | 'done' 已完成
  publisherKey: 'owner_xxx',      // 本机发布者标识
  views: 18,
  createdAt: 1759... ,            // 时间戳
  updatedAt: 1759...
}
```

### 3.2 存储键

| 键 | 内容 | 说明 |
| --- | --- | --- |
| `lf_items_v1` | item 数组的 JSON | 主数据 |
| `lf_owner_v1` | 本机发布者标识字符串 | 首次发布时自动生成 |

版本后缀 `_v1` 是为了以后改结构时能平滑升级，不用兼容脏数据。

### 3.3 状态机

```
        ┌───────────── updateStatus(id,'done') ─────────────┐
        │                                                   ▼
   ┌─────────┐                                        ┌──────────┐
   │ active  │◄────── updateStatus(id,'active') ───────│   done   │
   │ 进行中   │                                        │  已完成   │
   └─────────┘                                        └──────────┘
   寻物 → 寻找中 / 招领 → 待认领                     寻物 → 已找到 / 招领 → 已归还
   列表正常展示、显示联系入口                          列表置灰后置、隐藏联系入口
```

非法状态值（例如 `'deleted'`）一律拒绝并返回 `null`，不允许出现第三种状态。

## 四、关键实现拆解

### 4.1 组合搜索（store.js）

```js
function searchItems(opts) {
  opts = opts || {};
  var kw = String(opts.keyword || '').trim().toLowerCase();  // 处理空格与大小写
  var list = loadItems();

  if (opts.type && TYPES.indexOf(opts.type) >= 0) list = list.filter(...);
  if (opts.category)                             list = list.filter(...);
  if (opts.onlyActive)                           list = list.filter(...);
  if (kw) {
    list = list.filter(function (i) {
      var hay = [i.name, i.desc, i.place, i.category, Utils.typeLabel(i.type)]
        .join(' ').toLowerCase();          // 关键词同时覆盖名称/描述/地点/分类/类型
      return hay.indexOf(kw) >= 0;
    });
  }
  return sortItems(list);                   // sortItems 内部 slice()，返回副本
}
```

两个容易踩的点：

1. **`sortItems` 必须先 `slice()` 再排序。** 否则会就地改动 `loadItems()` 返回的数组，虽然那只是内存副本不影响存储，但会让"搜索结果不改变原始数据顺序"这条用例失败 —— 这类隐蔽副作用值得用测试锁住。
2. **非法 `type` 当作"不过滤"处理**，而不是返回空结果。用户从地址栏乱传参数时，页面应该展示全部而不是空白。

### 4.2 表单校验（store.js）

`isValidPublishData(data)` 返回 `{ ok, errors }`，`errors` 的键就是出错字段名：

```js
if (!len(data.name)) errors.name = '请填写物品名称';
else if (len(data.name) > LIMIT.name) errors.name = '物品名称不能超过 30 个字';
...
if (!len(data.time)) errors.time = '请选择丢失日期';
else if (!Utils.parseDate(data.time)) errors.time = '日期格式应为 YYYY-MM-DD';
else if (Utils.isFutureDate(data.time)) errors.time = '日期不能晚于今天';
```

界面层拿到 `errors` 后统一回显（`showFormErrors`）：给对应控件加 `.err` 类、把文案写进该字段的 `.err-msg` 槽、聚焦第一个出错字段、并弹一条 Toast 提示。**一次提交把所有错误都指出来**，而不是让用户改一个报一个。

还有一条硬约束：**校验不过就不写存储**。`createItem` 在 `!check.ok` 时直接返回，绝不落库，对应的用例是"createItem 校验不通过时不写入存储"。

### 4.3 联系方式的校验边界（被测试抓出来的 bug）

最初的规则是"手机号 或 邮箱 或 QQ(5-12位数字) 或 微信号"，结果 `1380000123`（少一位的手机号）因为满足"8 位纯数字"被当成合法 QQ 放行了。

修复思路：**所有纯数字串先按"手机号 / QQ"这一组规则判定**，顺序与失败条件都要明确：

```js
if (/^1[3-9]\d{9}$/.test(v)) return true;    // 11 位合法手机号
if (/^1[3-9]\d{8}$/.test(v)) return false;   // 想写手机号却少一位 → 非法
if (/^[\w.+-]+@[\w-]+(\.[\w-]+)+$/.test(v)) return true;
if (/^\d{5,11}$/.test(v)) return true;       // QQ 收窄到 5-11 位
if (/^[A-Za-z][A-Za-z0-9_-]{5,19}$/.test(v)) return true;
return false;
```

### 4.4 日期校验的溢出陷阱（第二个被测试抓出来的 bug）

`new Date(2026, 12, 1)` 不会报错，而是**静默溢出**成 2027-01-01。所以 `parseDate` 必须自己检查范围与溢出：

```js
if (mo < 1 || mo > 12 || da < 1 || da > 31) return null;
var d = new Date(y, mo - 1, da);
if (d.getFullYear() !== y || d.getMonth() !== mo - 1 || d.getDate() !== da) return null; // 2026-02-30
```

不这么写的话，用户手输 `2026-02-30` 会被悄悄存成 `2026-03-02`，等到列表里显示出来才发现日期不对。

### 4.5 一键复制（app.js）

```js
if (navigator.clipboard && navigator.clipboard.writeText) {
  navigator.clipboard.writeText(text).then(成功提示, fallback);
} else {
  fallback();   // 隐藏 textarea + document.execCommand('copy')
}
```

`file://` 协议或非 HTTPS 环境下 `navigator.clipboard` 可能不可用，所以必须有降级路径，并且**无论走哪条路都要给用户反馈**（Toast 提示"已复制"或"复制失败，请手动长按选中"）。

### 4.6 防 XSS（utils.js + view.js）

```js
function escapeHtml(str) {
  return String(str)
    .replace(/&/g, '&amp;').replace(/</g, '&lt;').replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;').replace(/'/g, '&#39;');
}
```

模板层里**所有**用户输入都走 `esc()`，例如 `<span class="item-name">' + esc(item.name) + '</span>'`。测试人员如果故意发布一条名字叫 `<img src=x onerror=alert(1)>` 的信息，它只会被当成普通文字显示。注意 `&` 必须最先替换，否则会把后面生成的实体再转义一遍。

### 4.7 存储不可用时的降级（store.js）

```js
var storageOK = (function () {
  try { localStorage.setItem('__lf_probe__', '1'); localStorage.removeItem('__lf_probe__'); return true; }
  catch (e) { return false; }          // 隐私模式 / 存储被禁用
})();
```

降级到内存对象 `memory`，功能照常，只是刷新后数据丢失（页面启动时会 Toast 提示一次）。另外 `loadItems` 对 `JSON.parse` 有 try/catch：万一存储被写坏，返回空数组而不是让整个应用白屏。

### 4.8 搜索输入的防抖（app.js）

关键词输入用 300ms 防抖，而且**只重渲染列表部分、不重渲染整页**，否则每敲一个字输入框就会失焦、光标跳到开头。标题里的结果条数单独更新，地址栏用 `history.replaceState` 同步（不产生历史记录，避免按一次返回键还在同一个页面）。

### 4.9 演示数据的播种（store.js）

```js
function seedIfEmpty() {
  var items = loadItems();
  if (items.length > 0) return { seeded: false, reason: 'already-has-data' };  // 绝不覆盖用户数据
  ...
}
```

只有"完全没有任何数据"时才播种。这条守卫是刻意加的：最初版本只检查"是否播种过"，结果用户清掉播种标记但保留了自己发布的信息时，刷新会**整体覆盖用户数据** —— 这是单元测试先跑出来的红色断言（`seedIfEmpty：已有数据时不覆盖用户数据`），修复后变成永久回归用例。演示数据的 `publisherKey` 统一指向本机标识，所以"我的发布"里立刻能看到内容并体验状态流转。

## 五、界面层路由表

| 路由 | 视图 | 说明 |
| --- | --- | --- |
| `#/` | 首页 | 列表 + 类型标签 + 只看进行中 + 两个发布入口 |
| `#/search?q=&type=&cat=` | 搜索 | 筛选条件放在 URL 里，搜索结果链接可分享 |
| `#/publish?type=lost\|found` | 发布 | 表单 + 校验回显；发布成功切到成功页（不跳路由，避免误刷新丢提交） |
| `#/edit/:id` | 编辑 | 复用发布表单；非本人信息通过地址栏直入会被拦下 |
| `#/detail/:id` | 详情 | 进入时浏览数 +1（用 `_countedViewId` 防止同一条重复计数） |
| `#/mine` | 我的发布 | 统计卡 + 每条信息的操作按钮 |
| `#/about` | 关于 | 功能清单、运行说明、清空/重载数据、页面内跑测试 |

事件统一用**事件委托**绑定在 `#views` 容器上（`[data-act]` 属性 + `switch` 分发），避免每次重渲染后重新绑定监听器。卡片本身也带 `tabindex="0"` 与 Enter/Space 键盘响应，键盘用户也能打开详情。

## 六、测试策略

- 分层的结果是**逻辑层可以白盒测试**：校验规则穷举边界，数据层覆盖增删改查与异常 id，搜索覆盖组合条件与排序，工具层覆盖转义与日期分档。
- 每个用例前 `resetStorage()`，用例之间零依赖、可乱序执行。
- `runTest()` 运行前备份 `lf_items_v1` / `lf_owner_v1`，`finally` 里还原，所以随时运行都不会毁掉演示数据。
- **未覆盖的部分**：`app.js` 的视图渲染与事件绑定没有被自动化覆盖，这部分靠浏览器实测补足（`docs/screenshots/` 里的截图就是实测记录：首页筛选、搜索实时筛选、发布校验、状态流转、我的发布、一键复制）。

## 七、踩坑清单（写博客时可以当"遇到的问题"素材）

| # | 问题 | 排查过程 | 解决与收获 |
| --- | --- | --- | --- |
| 1 | 少一位的手机号被当成合法 QQ 放行 | 单元测试断言 `1380000123` 非法却失败 | 纯数字串先判手机号 / QQ，QQ 收窄到 5-11 位；边界规则要"先写测试再写实现" |
| 2 | `2026-13-01` 不报错反而变成 2027-01-01 | 断言失败后打印 `parseDate` 返回值才发现 `Date` 会静默溢出 | 自己校验范围与溢出；**不要盲信 `new Date()` 的容错** |
| 3 | 播种演示数据会覆盖用户已有数据 | 用例 `已有数据时不覆盖用户数据` 断言失败 | 加"已有数据一律不播种"守卫；存储层"不覆盖用户数据"是底线，用测试锁死 |
| 4 | 一个用例抛异常导致后面全部不执行 | 单 `try/catch` 包住整个 for 循环 | 改成每个用例独立 `try/catch`，失败互不影响，一次能看到全部红色用例 |
| 5 | 搜索框输入每个字都失焦 | 输入时整页重渲染，焦点被新节点顶掉 | 只重渲染列表容器，输入框不动；并用 300ms 防抖 |
| 6 | 用 `hidden` 属性藏返回按钮却不生效 | `getComputedStyle` 显示 `display:grid` —— `.icon-btn` 的 `display` 覆盖了浏览器默认的 `[hidden]` 规则 | 写 `.icon-btn[hidden] { display: none !important; }`；教训是**不要随口说"刷新一下就好"，先用计算样式确认** |
| 7 | 页面内跑测试时结果里混着 `%c` 和 `color:...` | `console.log` 的样式参数被一起收集了 | 收集日志时过滤样式参数并去掉 `%c` |
| 8 | 测试会清空 localStorage，可能弄丢演示数据 | 想到助教可能在看页面的同时跑测试 | `runTest()` 前后备份 / 还原数据，并补一条实测验证（跑完 6 条数据仍在） |
| 9 | 清空数据后刷新演示数据又回来了 | `seedIfEmpty` 在页面启动时无条件执行 | 保留该行为但明确按钮语义：「清空本机数据」清空为止，「重新载入演示数据」才重新播种 |
